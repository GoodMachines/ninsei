## 2026-11-04
- **Neighbours the brief didn't list:** `huddo` (people + agents in one group chat, hosted on api.huddo.ai, MCP) and `index-network` (agents matching people by interest) are already in the catalog. Hearth's differentiators are therefore: native Desktop UI, no server ($0), budgets in code, the offer → build → Share loop, games.
- **Transport spike:** results are in PLAN.md. Pure-Python BIP-340 signing works, and no new Python deps are needed: Hermes's runtime env (Python 3.14, under `~/.hermes/installs/.../venv`) already has websockets 15, aiohttp, cryptography. Note `~/.hermes/hermes-agent/venv` is a stale 3.11 env and is not what Hermes runs on.
- **Process model spike:** under `hermes dashboard --isolated`, `register(ctx)` and `dashboard/plugin_api.py` share a PID, and `ctx.llm` works from a route (via `asyncio.to_thread`). `plugin_api.py` is imported by file path as `hermes_dashboard_plugin_hearth`, so relative imports don't work. Both halves load the engine through `_loader.py` under one private module name, `hearth_room_engine`. The no-core-override lint only flags `sys.modules[...]` writes to Hermes module names, so this is allowed.
- **Test profiles:** `hearthmaya` was cloned from default, with plugins trimmed to just `hearth`. The repo is symlinked into `~/.hermes/profiles/hearthmaya/plugins/hearth`. The default profile's config is unchanged (checked).
- **Rules on multiple entries:** not found publicly. The typeform only shows a start page; question for Justin.
- **Game:** switched from trivia to a bluffing game (Tall Tales) after review. The fake-answer mechanic is an old parlour-game genre; names and content are original.
- **Core already has group rooms (Bot Mode, `user-guide/bot-mode.md`); I checked them and didn't reuse them.** A group chat seats 2–6 of one person's own bots. Spanning machines needs that person's Connections or `hermes peer` with API keys, plus network reachability. Members are full agents with tools, which SECURITY.md §2.6 says not to expose to strangers' text. The core **Buzz adapter** is also Nostr-based, but it needs a hosted Buzz community membership and a Rust binary, and it pipes text into the full agent. Hearth's niche stands: many people, strangers welcome, $0, tool-less room brain. The README should say this plainly. (A Claude Prime research message raised these; each was verified locally.)

## UI (agent)
- **One source, two outputs, no npm.** `ui/*.js` is plain JS written against two tiny interfaces: `P` (platform: rest, timers, toasts, clipboard, storage, animation loop, `openBuild`) and `K` (kit: Button, Input, Dialog, Icon, Tip, Toggle, Toy). `scripts/build_ui.py` concatenates `ui/platform/<kind>_head.js` + `ui/*.js` + `<kind>_tail.js` into `desktop/plugin.js` (ESM) and `dashboard/dist/index.js` (IIFE), unminified, and refuses JSX or non-SDK imports. `--check` exits 1 when an output is stale.
- **Desktop imports the SDK as a namespace** (`import * as sdk`) so newer pieces (`registerSettingsPage`, `host.composer`, `createBudgetedLoop`, `ToggleRow`, `pet`) are feature-detected instead of failing module load on an older Desktop.
- **Theme:** every colour is a `--h-*` token mapped per platform onto `--ui-*` (Desktop) or `--color-*` (dashboard). Agent colour = the theme's own foreground rotated to the agent's hue (`oklch(from var(--h-fg) l 0.15 H)`) mixed 64% into the background, so faces read mid-tone on light and dark themes; plain accent is the fallback where relative colour syntax is missing.
- **Motion:** one damped-spring solver (semi-implicit Euler, 240 Hz substeps) on one shared loop that parks when nothing moves (`createBudgetedLoop` on Desktop, a self-parking rAF in the browser). Springs write to the DOM directly, never re-render React. Used for message/draft/toast entrance, the budget ring, the countdown ring, a face "pop" on state change, and scrolling a running toy into view. Face idle loops (blink, scan, talk, clock) are CSS keyframes. `prefers-reduced-motion` jumps springs to their target and stops keyframes.
- **Live updates:** Desktop listens to `plugin.hearth.changed` and polls `/state` (5 s with no Hearth view mounted, 2 s with one, 1 s while a game runs); the browser polls on the same schedule. A snapshot identical to the last one does not re-render.
- **Dashboard sizing:** the tab mounts inside the dashboard's scrolling `<main>`, so the page measures its own top edge and sizes to the rest of the window; only the timeline and the pinned stack (game, drafts) scroll.
- **Verified in the browser** (dashboard tab, Maya on :9311 and Sam on :9312): room, Lobby, card preview, settings, toy Run in a sandboxed iframe, narrow layouts. Vote/reveal/fakes phases, impostor chip, budget line, drafts tray, open offer and the review dialog were checked by patching `SDK.fetchJSON` in the page to inject those states (no extra model spend). **Not verified:** anything Desktop-only (route, nav row, status chip, palette, settings page, pet line, composer hand-off); it is built against the docs and `sdk/index.ts`.
- **API gaps noticed (not changed):** game `ends_at` has no phase start or duration, so the countdown ring takes its full length from the longest remaining time it has seen; reveal `authors`/`picks` are pubkeys only, so names come from the room's member list (a player who left shows as "someone"); both test agents still carry the engine default face (`hue 28, round`), so Ada and Bo look alike until someone picks a face.

## Widgets + theme (agent)

- **Chat cards.** Two transcript directives, registered on `sdk.TRANSCRIPT_DIRECTIVE_AREA` (skipped on a Desktop without it): `::hearth-offer{id="<64-hex offer id>"}` and `::hearth-tales{room="<room id>"}`. Attribute values need double (or single) quotes, or Desktop's parser ignores them. Code is `ui/65_cards.js`, registered in `desktop_tail.js`; the dashboard bundle carries the code but never registers it.
- **Untrusted attributes.** Shape check (64-hex / 8-64-hex), then a lookup in the backend's own `/state`; a miss renders a small "Hearth: not found" chip, a missing backend renders "Hearth: not available". All text is rendered as text.
- **Offer card.** Title, pitch, state, owner. Yours + open: Accept (calls `/offers/answer`, then the same `P.openBuild` hand-off as the Hearth page: new chat, task in the composer, nothing sent) and Not now. Ready: Share to room, with an inline "Share the built file with #room?" confirm because there is no preview here. Other people's offers are read-only.
- **Tales card.** Reuses `TallTales` (fake/vote/reveal/scoreboard) with a card-local store whose `post` hits `/game/fake` and `/game/vote`; polls `/state?room=` every second. `autoFocus` is off in cards (`quiet`), so a card appearing never steals the composer.
- **Hidden turns: not wired up the way the brief assumed.** `window.hermes.send()` exists only inside the sandboxed preview frame (`inline-preview-directive.tsx` injects it). A plugin React component runs in the app window, where nothing defines it, and the SDK's `host.composer.submit()` sends a visible turn (no `displayKind: 'hidden'` option). So `tellAgent()` feature-detects `window.hermes.send` and does nothing when it is absent, rather than posting visible chatter. Decline and share call it (<=500 chars, one per second); Accept does not, because it moves to a new chat. Backend routes do all the real work.
- **Read side effect.** `/state?room=` marks that room read. The offer card therefore only fetches a room when it has nothing cached or the offer changed state; the tales card fetches its room every second while mounted (viewing it counts as reading).
- **Getting directives into chats.** `build_prompt` now tells the agent to open its reply with the offer directive (test added). `hearth_status` returns `chat_cards`: offer directives for open/building/ready offers, a tales directive per room, and a one-line how-to. The model only has the store (no live game state), so the how-to says to use a tales line only when it is telling the user about a running game.
- **Theme "Hearth"** (`name: 'hearth'`, `sdk.THEMES_AREA`; light and dark palettes). Warm paper (#f6efe4) and banked embers (#1f1a17), accent derived from Hearth's default agent hue (28). Listed in the picker only; nothing calls `setTheme`/`requestTheme`. Contrast checked with the WCAG formula the SDK's `contrastRatio` uses: every text pair >= 5.0:1 (lowest: primary on card, light), most 6-12:1.
- **Not verified in the app:** the directive rendering, button flows, the `window.hermes` availability, and the picker entry. All checked statically against `transcript-directive.tsx`, `lib/transcript-directives.ts`, `themes/types.ts` and `user-themes.ts`.
