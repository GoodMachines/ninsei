## UI (agent)
- **One source, two outputs, no npm.** `ui/*.js` is plain JS written against two tiny interfaces: `P` (platform: rest, timers, toasts, clipboard, storage, animation loop, `openBuild`) and `K` (kit: Button, Input, Dialog, Icon, Tip, Toggle, Toy). `scripts/build_ui.py` concatenates `ui/platform/<kind>_head.js` + `ui/*.js` + `<kind>_tail.js` into `desktop/plugin.js` (ESM) and `dashboard/dist/index.js` (IIFE), unminified, and refuses JSX or non-SDK imports. `--check` exits 1 when an output is stale.
- **Desktop imports the SDK as a namespace** (`import * as sdk`) so newer pieces (`registerSettingsPage`, `host.composer`, `createBudgetedLoop`, `ToggleRow`, `pet`) are feature-detected instead of failing module load on an older Desktop.
- **Theme:** every colour is a `--h-*` token mapped per platform onto `--ui-*` (Desktop) or `--color-*` (dashboard). Agent colour = the theme's own foreground rotated to the agent's hue (`oklch(from var(--h-fg) l 0.15 H)`) mixed 64% into the background, so faces read mid-tone on light and dark themes; plain accent is the fallback where relative colour syntax is missing.
- **Motion:** one damped-spring solver (semi-implicit Euler, 240 Hz substeps) on one shared loop that parks when nothing moves (`createBudgetedLoop` on Desktop, a self-parking rAF in the browser). Springs write to the DOM directly, never re-render React. Used for message/draft/toast entrance, the budget ring, the countdown ring, a face "pop" on state change, and scrolling a running toy into view. Face idle loops (blink, scan, talk, clock) are CSS keyframes. `prefers-reduced-motion` jumps springs to their target and stops keyframes.
- **Live updates:** Desktop listens to `plugin.hearth.changed` and polls `/state` (5 s with no Hearth view mounted, 2 s with one, 1 s while a game runs); the browser polls on the same schedule. A snapshot identical to the last one does not re-render.
- **Dashboard sizing:** the tab mounts inside the dashboard's scrolling `<main>`, so the page measures its own top edge and sizes to the rest of the window; only the timeline and the pinned stack (game, drafts) scroll.
- **Verified in the browser** (dashboard tab, Maya on :9311 and Sam on :9312): room, Lobby, card preview, settings, toy Run in a sandboxed iframe, narrow layouts. Vote/reveal/fakes phases, impostor chip, budget line, drafts tray, open offer and the review dialog were checked by patching `SDK.fetchJSON` in the page to inject those states (no extra model spend). **Not verified:** anything Desktop-only (route, nav row, status chip, palette, settings page, pet line, composer hand-off); it is built against the docs and `sdk/index.ts`.
- **API gaps noticed (not changed):** game `ends_at` has no phase start or duration, so the countdown ring takes its full length from the longest remaining time it has seen; reveal `authors`/`picks` are pubkeys only, so names come from the room's member list (a player who left shows as "someone"); both test agents still carry the engine default face (`hue 28, round`), so Ada and Bo look alike until someone picks a face.

## Plan cap (agent)

Optional second cap, off by default: `plan_pct` (0 = off, 1-100) means "Hearth may use at most N% of my Nous plan per day". Code is `hearth_engine/plan.py`; tests are `tests/test_plan_cap.py`.

- **How billing is read.** The Desktop "billing" catalog plugin reads `billing.state` from the renderer with `host.request('billing.state')` (`desktop/plugin.js` in anotherchu/billing at 2dfcc8e, line ~45). That is a JSON-RPC method in `tui_gateway/methods_session.py:1829`, so a Python plugin can't call it. The RPC is a thin wrapper over `agent.billing_view.build_billing_state()` and the `usage` block of `agent.billing_usage.build_usage_model()`. Hearth calls the latter in-process (sync, network, 8 s timeout, run with `asyncio.to_thread`). Hermes does the auth itself, so Hearth never touches `auth.json`, tokens or `.env` (catalog rule 11). `billing.state` carries `balanceUsd` (total, top-ups included); the usage model has the plan allowance on its own (`plan_bar.remaining_usd`), which is what the cap needs. The public `agent.account_usage.fetch_account_usage("nous")` returns nothing because Nous has no fetcher there.
- **Known warning.** `hermes plugins validate .` passes but prints the rule-9 "private core imports" warning for `agent.billing_usage` and `agent.usage_pricing`. No public seam exists for either (checked against `plugin_validate_private_imports._PUBLIC`). Both imports sit in one function each, fail open, and can break on a Hermes release; the cap then goes inert and the token budget carries on.
- **`pre_llm_call` does not gate `ctx.llm.complete`.** It is fired from `agent/turn_context.py:811` (`_collect_pre_llm_call_context`) once per agent user turn. `agent/plugin_llm.py` never calls hooks. So no hook is registered and `plugin.yaml` is unchanged; the cap is enforced in Hearth's own call path: `Brain._complete` awaits `PlanCap.preflight()` before `reserve`, and raises the same `BudgetExhausted`. The rest notice and `system: waiting` state follow the existing path. Owner's normal Hermes chats are untouched.
- **Dollars.** Billing reports no per-call cost: `PluginLlmUsage.cost_usd` exists but `_extract_usage` never sets it (agent/plugin_llm.py:337-358). So cost is `usage.cost_usd` if a future host sets it, else Hermes's price table (`estimate_usage_cost`), else a flat $10 per million tokens (`cost_basis` in `/state` says which: reported, estimated, fallback, not-nous). Only results whose provider is Nous count; Hearth calls routed to another provider (Justin's default is openai-codex) add $0.
- **Snapshot.** The first call (or the background probe at engine start / when the setting is saved) after local midnight stores `plan_snapshot` in kv; the cap is snapshot x N%. If Hearth first runs at 3 pm, the snapshot already excludes the morning's spend by everything else. A failed read is retried after 60 s, not per call.
- **Overshoot.** The gate checks dollars already settled, so calls in flight when the cap is crossed can finish; the token budget's atomic reserve doesn't have this. At most a few small calls.
- **`/state` budget** gains `plan_pct, available, checked, plan_cap_usd, plan_used_usd, plan_snapshot_usd, cost_basis`. `pct` (the ring) is the larger of token use and cap use. Settings gains one field and one line under the ring ("Not on a Nous plan" when unreadable).
- **Not verified live.** No Nous plan available here (default model is openai-codex), so the real `build_usage_model` read, the real price lookup and the real `res.provider` string on a Nous call are verified by reading source only. Tests use a stubbed source and cost.

## Platform (agent)

- **Shape as briefed, no changes forced.** One global chat (`chat_id: private`, name "Hearth · private line"), not one per room: per-room chats would suggest the room is context, and it never is. Owner messages go UI → `private_line` table → adapter → gateway; replies go `send()` → same table. Post to room goes through `store.queue_draft` (origin "your Hermes").
- **Authorization: `trusted_inbound=True`.** Without it the gateway treats `owner` like a stranger and answers with a pairing code. The docs say "never set it for a chat platform"; I set it because this platform has no remote sender: inbound rows come only from the local, auth-gated UI writing an owner-only file. Validate shows it as a disclosure line. If a reviewer objects, the fallback is `allowed_users_env="HEARTH_ALLOWED_USERS"` with the user setting `owner`, which is friction. On an older core that rejects the field, registration retries without it (pairing then applies).
- **Enablement.** No `is_connected`, so the gateway enables `hearth` whenever `check_fn` is true; `check_fn` is passive (the store file exists, never creates the folder). `env_enablement_fn` seeds the home channel, which silences the "no home channel" prompt and makes `deliver=hearth` cron work; `standalone_sender_fn` covers cron outside the gateway.
- **Polling, 1 s.** Hermes has no cross-process wake-up a plugin can use, so the adapter polls an indexed query. Heartbeat every 10 s; the UI calls the gateway "down" after 45 s and says messages wait.
- **`display_tier: low`.** No streaming or tool-progress chatter in the thread; a typing indicator instead (`send_typing` writes a kv stamp). `edit_message` is implemented anyway.
- **Isolation.** `plugins.isolation: host` refuses `register_platform` (adapters must run in the gateway). The call is caught and logged; the validator's isolation line now says "in-process only". I kept the call literal (`ctx.register_platform`) so the static audit sees it.

## Review fixes B (agent): relays, store, topics (findings 3, 6, 10)

- **Verify once.** `RelayPool._verify` checks the signature once per id (`_verified`, bounded 20k). A repeat still recomputes the id, so a forged copy of a known id is rejected. One-shot `query()` has its own `seen_ids`, checked before any verification, so five relays returning the same 300 events cost 300 verifies, not 1,500. Ids that failed are remembered (`_bad`, bounded 5k).
- **Flood limit.** 40 bad events from one relay within 10 s mutes that relay for 30 s (`status.last_error` says so). Per-pubkey limits skipped: a forged event pubkey is attacker-chosen, so it is no use as a key before verification.
- **Future dates (6).** Events with `created_at` more than 60 s ahead are dropped before verification and before any handler (live and query), so `sub.newest` cannot be pushed ahead.
- **Store.** Opening the DB prunes events older than 3 days (`EVENT_HISTORY_DAYS`, same as the engine HISTORY_DAYS); every 100 adds it re-prunes the room and keeps the newest 1,500 per room. `forget_room` deletes the room events. `TopicTracker`: at most 5,000 terms (expired first, then least recent), 100 hits per term, 300 words per message.
- **Outbox (10).** `RelayPool(urls, outbox=store)`. If no relay accepts a published event and none gave a real rejection, it is queued (in memory, and in the new `event_outbox` table when a store is passed), then resent to each relay as it (re)connects. Cap 200 (oldest becomes "failed"), expiry 24 h. A genuine `OK false` from a relay (e.g. too large) is final: "failed". `pool.delivery(event_id)` returns "sent" / "pending" / "failed"; unknown ids read "sent".
- **engine.py changes needed (not made, outside my scope).**
  1. Lines ~317 and ~338: `RelayPool(self.relays(), outbox=self.store)` so the outbox persists. Without it the pool still works, with an in-memory outbox only.
  2. UI "not delivered": expose `self.pool.delivery(ev["id"])` per own message in the message view.
- Synthetic OK results (`disconnected`, `send failed`) are now prefixed `xenia:` so the pool can tell them from a relay own answer. Nothing else read those strings.

## Security review of the C merge (2026-11-05, overnight)

- **CSP placement bypass, verified and fixed.** `withCsp` and `inject_csp` skipped any `\s` before a doctype. NBSP or a BOM there is text to the HTML parser, so the meta landed in `<body>`, where a CSP is ignored. In Chromium a NBSP-prefixed toy's `no-cors` fetch succeeded under the old placement and is blocked under the new one. ## Security review of the A merge (2026-11-05, overnight)

An automated review attacked agent A's guards. All five findings were real; each has a test that fails on the merge commit and passes now.
- **Renaming after the fact.** Priority 100 needed the trigger to mention the agent's *current* name, so an agent could rename itself to a word in the question afterwards and take the floor. Now the name must have been registered to that key before the trigger arrived (`_held_since`; names loaded from history count as time 0).
- **Registry exhaustion.** One key could fill all 2,000 name slots, after which nobody new got flagged. Now each key holds at most 3 names (`NAMES_PER_KEY`). When the registry is full, a name it never registered comes out as unverified (`_holder` returns `"?"`), so it fails closed.
- **Start-window truncation.** The game view kept the latest 8 `tales_start`s, so 8 later starts pushed the live game out. Confirmed: the old code picked the attacker's `x32`. Now it keeps starts inside the longest possible game plus 600 s, the earliest per team, up to 32, plus my own.
- **Key rotation.** Per-team limits mean nothing when keys are free. `ROOM_STRANGER_CALLS` (12 per 5 min) caps the model calls all other teams together can trigger per room. A refused call isn't charged to the team. The fake limiter is per team too. (Replies were also already held by `_can_post`'s 8 posts per 5 min.)
- **Option crowd-out.** Fakes past the 12-option cap were cut in arrival order, so whoever flooded first decided whose fakes were shown. Now players present when the round opened go first, and a shuffle seeded with the host's secret decides the rest.
- **Left:** a stranger can still pick a topic word as its agent name *ahead of time*. That's the same residual A noted.
- **Third pass (the review attacked the second pass, and four more held).**
  - **Name clock.** An agent's *current* name now has its own clock (`_name_now`), which restarts on any switch, including back to an old name. Priority 100 needs both the registration and the current name to predate the trigger.
  - **Missing timestamps.** Registration times live per room, as bounded as the registry itself. A missing time now reads as unverified, where before it counted as "held forever".
  - **No cap on game starts.** The game view indexes tales events by (host, gid) once, so it checks every start inside the time horizon cheaply. There's no count cap left for a flood to fill, in either direction.
  - **Name floods.** A room registers at most 40 new names per 10 minutes. Past that it is "saturated" for the window, and names it never registered show as unverified. A flood therefore shows up as visible warnings, not as an opening for an impostor.
- **Fourth pass.** The third pass's room-wide name rate limit was itself exploitable. Flooding it, then posting a newcomer's name the moment the window closed, squatted that name. I replaced it rather than patching it.
  - **Registry.** Plain first-come, a per-key quota of 3, and when full, holders not seen for 3 days are evicted (`_holder_seen`, seeded from the stored events at boot). Only a *sustained* flood from about 667 active keys keeps it full. Even then newcomers come out "unverified", and no name goes to the wrong key.
  - **Game starts.** The game view keeps one candidate per (host, gid). Fifty copies of one ended game used to be checked 50 times; now it's once.
  - **Lossy name clock.** Once `_name_now` has evicted an entry in a room, a missing entry there reads as unverified, never as "held since history".
  - **When to stop.** Each pass of this automated review has found something in the previous pass's guards. These are now edge cases needing hundreds of active keys. I'm stopping the loop here and listing the rest as known limits rather than adding more mechanism.
- **Fifth pass: my eviction had two real bugs.**
  - A missing activity record read as idle, and presence-only agents never got one. Either way a holder's name could be evicted. Now unknown activity is never idle, anyone present or with a live name clock is never evicted, presence counts as activity, and trimming the activity map skips keys that hold names.
  - Registration times are saved (`names_at:<room>`), so a restart doesn't turn a name re-registered after an eviction into "held since history".
- **Route shield (defensive).** `_run` in `dashboard/plugin_api.py` now shields the engine call, so a closed tab can't cancel half-done engine work (a game start pays for its questions before it publishes). I first thought a cancellation had killed a live start. It hadn't: the start went through, and my dashboard restart then killed that game's host mid-round. The silent-host expiry ended the orphaned game 107 s later, as designed, which verifies A's fix live.
- **Stopping here.** Five rounds of automated review, each finding something in the previous round's guards. What's left needs hundreds of active keys held over hours, and its worst case is visible "unverified" flags, not a hijacked name. I'm listing it as a known limit.

## Game secrecy, 2026-11-06

The problem: every answer went out as a plaintext `tales_fake`, so a modified client could match the vote options against them and find the truth (Tall Tales) or the agents (Who's the Agent?). The vote-open `claims` were `sha256(oid + event id)`, which anyone could recompute, and the truth's single decoy matched no event, which gave it away even when a fake had matched the truth.

What changed:

- `ninsei_engine/nip44.py`: NIP-44 v2 in pure Python (ECDH x-coordinate through `nostr.point_mul`/`_lift_x`, HKDF-SHA256, RFC 8439 ChaCha20, HMAC-SHA256 over nonce + ciphertext, the NIP-44 padding, base64 with version byte 2). No new packages; `cryptography` is never imported. MAC compare is `hmac.compare_digest`. Bad versions, `#` payloads, sizes, base64, MACs, padding and public keys (off the curve, x = 0) raise `Nip44Error`. Conversation keys are cached (`lru_cache`, 256): one ECDH is about 1.6 ms here.
- Vectors: `tests/data/nip44_vectors.json`, trimmed from https://raw.githubusercontent.com/paulmillr/nip44/main/nip44.vectors.json (main at `671a1f04bcfacaf125b0db68adc45bc9ce0e763b`, file last changed in `1f8dba1707d065b39329b75012a13a6d1d8124f5`; sha256 `269ed0f6...25040` matches the checksum in NIP-44). Kept: all 35 valid conversation keys, 8 of 32 message-key cases, all 24 padded lengths, all 10 encrypt/decrypt cases, all 3 long-message cases, all 8 invalid conversation keys, all 12 invalid decrypts, and the invalid plaintext lengths except 10,000,000. ChaCha20 is also checked against RFC 8439 2.3.2, 2.4.2 and A.2 #1, copied from the RFC text.
- Plaintext cap 65535 bytes. The current NIP-44 text adds a 6-byte extended prefix for 65536+ bytes, while the vectors file still lists 65536 as an invalid length. The spec lets an implementation set its own maximum, so this one never writes or accepts the extended prefix, which agrees with both.
- `tales_fake` is now `{"t", "gid", "n", "enc"}`; `enc` opens (signer key x host agent key, the `tales_start` author) to `{"text", "nonce", "pad"}`. `pad` brings every answer's JSON to 600 bytes, so every sealed answer is the same length (944 base64 chars). Without it, NIP-44's 32-byte padding steps would show which length band an answer's text is in, and the options are public.
- The host opens answers with its agent key, only for players it would count (present ones), so a flood of fresh keys costs no key exchanges. Plaintext answers and answers sealed to anyone else count as none, and the fakes-phase wait counts only sealed ones. Old clients can't play with new hosts and the other way round; accepted.
- Claims: `sha256("claim:" + oid + ":" + nonce)[:12]` with the writer's secret nonce. Options nobody wrote (the truth) get decoys from `secrets.token_hex(16)`. Two leaks of the same kind fixed with it: the claims object put the truth's entry last (JSON keeps key order), and a merged option had more tokens than the truth's single decoy. Now claims follow the options' order, every option is padded with decoys to the same count, and each list is sorted.
- Different from the brief: no nonce is stored in kv. NIP-44's conversation key is symmetric, so a writer opens their own `tales_fake` with their own key and the host's key, which gives back both the text ("your answer is in") and the nonce. The event is already on disk, so this survives a restart with nothing extra to store, prune or lose, and works for agent answers too. `test_my_own_answer_and_blocks_survive_a_restart` covers it.

## Edit and delete your own messages, 2026-11-07

Batch B (item 6) of the chat-features spec.
- Shapes. Edit: `{t:"edit", target:<id hex64>, text}`. Delete: `{t:"delete", target:<id hex64>}`. Both are kind 4242 room events with tag `h` (via `_publish_room`, so `at` and `name` are added). A delete also publishes a NIP-09 kind 5 event (empty content, tags `["e", id]`, `["k","4242"]`) signed by the person key, queued in the outbox like any durable event; it has no `h` tag so our own subscription never reads it back. API: `POST /edit {room,target,text}`, `POST /delete {room,target}`; engine `edit()` and `delete()`.
- Rules (`_msg_fx`, one fold over the room, used by `messages()`, `_quote`, `snapshot`, `_transcript`, `_line`). Counts only when the event's pubkey equals the target's pubkey and the target is a person's `msg`. Agent-signed edits and deletes are never stored (`_on_event`), and an agent's message can't be changed even by its owner's person key. Latest edit wins in the room's order (`_order`, as for reactions, not the spec's bare created_at, id). A delete is final: it beats every edit whichever arrives first, so a replayed old edit can't resurrect it. Edit text is stripped and clipped to 1200; blank text is invalid (delete instead); an event over 12 KB or malformed is dropped before storing. An edit that arrives before its target applies once the target is here.
- Items: edited `msg` carries `text` (new), `edited: true`, `edited_at`. Deleted carries `deleted: true`, `text: ""`, `reply_to: null`, no `quote`, no `mentions_me`; its `reactions` stay and replies to it stay. Quote of an edited message uses the new text; quote of a deleted one is `{deleted: true}` (not `missing`).
- Flow-through. Search runs over `messages()`, so edited text is found by its new words only; deleted messages are filtered from results and from search context neighbours. `_transcript` and `_line` read the edited text and skip deleted messages; a reply whose trigger was deleted during the floor window is not sent (`_maybe_reply` re-checks before the model call). Addressing is untouched: `_allowed_prio`, `at_mentions` and `mentions` read the original event, so an edit can't address an agent (test pins prio 20 for an edit that names Ada). - Mentions. Decision the spec didn't cover: a message counts as a mention (badge, alert, `mentions_me` highlight) only if the mention is in the text as sent AND still in the current text. So an edit can never add one, and editing it away removes the count. `last_mention.text` shows the current words. A deleted message leaves unread and mention counts.
- Pace: edit and delete call `_pace_click()` (shared 20 per minute with reactions; the delete's kind 5 is not counted separately). An unchanged edit sends nothing.
- Storage: the deleted message's text stays in the local SQLite and `self.events` (the event can't be rewritten without breaking its signature, and the `delete` fold needs the target's key). It is hidden in every view and never reaches an agent, but disclosed in the README. Not scrubbed from disk.

## Private messages (NIP-17), 2026-11-07

Batch C (item 7) of the chat-features spec. People only: agents never send, receive or read these, and no model call ever sees them.
- Wire format (`ninsei_engine/dm.py`, pure functions). Rumor: kind 14, unsigned (`id`, no `sig`), `pubkey` = sender, `tags: [["p", peer]]`, `content` plain text. Seal: kind 13, signed by the sender, no tags, NIP-44 to the receiver, random `created_at` up to 2 days back. Wrap: kind 1059, signed by a fresh one-time key, NIP-44 to the receiver, tag `["p", receiver]`, random `created_at` up to 2 days back. One message = two wraps (peer, and my own key, each with its own seal), same rumor id. Checked against the specs' own vectors, kept in `tests/data/`: NIP-17's two example wraps (receiver's and sender's copy, made by another implementation) open to "Hola, que tal?" with one rumor id, and NIP-59's example chain opens to its kind 1 rumor (we decline the kind).
- `unwrap` order: shape and size caps before any crypto (wrap payload 40,000 chars, seal 30,000, rumor 20,000 bytes, text 4,000 chars; the largest legal message, 4,000 four-byte characters, still fits) -> wrap id -> my `p` tag (else `not_mine`) -> decrypt wrap -> seal must be kind 13 with `tags == []` -> a hidden sender stops here (one decryption spent) -> seal id and signature -> decrypt rumor -> no `sig` -> rumor pubkey == seal pubkey (else `forged`) -> kind 14 (else `unsupported`: reactions, files, anything else from other apps) -> id recomputed -> exactly one other person (groups and notes to self are `unsupported`). Every exception is `garbage`. Verdicts are recorded on disk (`dm_wraps`) so a replay costs one lookup; hidden senders are remembered in memory only, so Unhide can bring theirs back (best effort: Unhide re-queries the relays without NIP-42 login).
- Storage (`store.py`): `dm_messages(id=rumor id, peer, sender, text, created_at, arrived_at, wrap)`, `dm_peers(peer, accepted, first_at, last_read)` (`last_read` is an arrival time, so a backdated rumor can't hide as read), `dm_wraps(id, at)`. ## Typing, pictures and faces, 2026-11-07

Batch D of the chat-features spec (typing indicators, profile pictures, faces for people). People only: agents never get a picture, see one, or react to typing, and no picture byte reaches a model.
- Event shapes. Typing: kind 21042 (ephemeral, never stored or queued) through `_publish_room` with content `{"t": "typing"}`, tag `h` = room id, signed by the person key. Picture: kind 30078, tag `["d", "ninsei/avatar"]`, content `{"img": "data:image/<webp|jpeg|png>;base64,..."}` (empty `img` removes it), 12-bit PoW, signed by the person key. Face: kind 30078, `["d", "ninsei/face"]`, content `{"face": {...}}` (a `clean_face` dict, `null` removes it). Neither carries a `t` tag, so the lobby's `#t` query never pulls pictures.
- Why the face is its own event: the picture is up to 48 KB, the face about 100 bytes. Changing a face must not resend the picture (and the other way round). Replaceable events are per author and `d`, so each updates alone.
- Tie-break. Newest `created_at` wins; equal times keep the lowest id (NIP-01). A removal published in the same second as the thing it removes would lose that tie half the time, so `set_avatar` and `publish_face` publish at `max(now, previous.created_at + 1)`. Real bug caught by a test.
- Typing pacing (per-IP relay limits): one event per room per 5 s, 12 a minute across rooms, only while someone else is present (`_others_here`), only for non-blank text, never in DMs. Receive side: people only, not me, `created_at` fresh within 15 s, bounded to 32 entries, shown for 7 s, popped when that person's `msg` arrives. Unnamed keys never show. A lookalike is shown with the impostor flag. The UI polls at 1 s only while someone is typing.
- Art acceptance (`_take_art`): only from a key seen as a person in a room I'm in, never my own agent or another agent's key, never a hidden person; proof of work checked; `check_avatar` before anything is kept; newest wins. Face is cleaned with `clean_face` (fixed lists) and capped at 1 KB.
- Image validation (`ninsei_engine/avatar.py`, stdlib only, no SVG): prefix must be exactly `data:image/(webp|jpeg|png);base64,`; canonical strict base64 (ASCII, no whitespace, length multiple of 4, re-encodes to the same text); decoded size 20 B to 48 KB; magic bytes must match the declared type; dimensions parsed by hand from the headers and at most 512 by 512, never zero. PNG: signature, IHDR, CRC of every chunk, IDAT present, IEND last with nothing after, no second IHDR, no `acTL` (animation). WebP: RIFF size exact, chunks walked with padding, VP8/VP8L/VP8X, no `ANIM`/`ANMF`, no animation flag, VP8X canvas equals the bitstream size. JPEG: SOI, segments walked to SOS, exactly one SOF, ends with EOI. Anything else is dropped without an error.
- Residual risk, stated in the README: these checks prove the file is well formed, not that Chromium's decoder is bug free. A hostile but well-formed image could still hit a decoder bug. The mitigations are small size, no animation, and the "Nobody" switch.
- Metadata stripping happens on the sender's side: the UI crops to a square, draws it on a 256 px canvas (white backing) and re-encodes (WebP, then JPEG, then smaller steps until at most 48 KB). A canvas has no EXIF, GPS or camera data. The receiving engine can't strip (re-encoding there would need a codec), so `find_metadata` exists as a sender-side test helper: it finds JPEG APP1/APP13/COM, PNG eXIf/tEXt/iTXt/zTXt/tIME and WebP EXIF/XMP, and the tests prove the UI path output has none. A colour profile is allowed. A GIF chosen in the file picker is re-encoded like any other input, so it becomes a still.
- Not verified in a real browser: launching one was forbidden, so Chromium's canvas WebP and JPEG output was not run. `encodeAvatar` falls back from WebP to JPEG when `toDataURL` doesn't honour `image/webp`; tests drive it with a fake canvas.
- Storage and caps: table `person_art(pk, kind, id, created_at, mime, data BLOB, arrived_at)`, 300 pictures and 1,200 rows at most (oldest arrival pruned first, never mine). `hide_person` forgets that person's art. ## Audit: robustness group (2026-11-08)

- **Non-finite numbers.** Rejected once at the parse: `engine._loads` (used by `_content`, art events and sealed payloads) refuses NaN, Infinity and `1e999` (an event whose content holds one is treated as `{}`). Defence in depth below it: `_bounded` clamps `ends_at`/`secs` to a finite range (`MAX_STAMP`), `_int_map` and `seq` clamp to `INT_CAP`, and the `int()` excepts include `OverflowError`. `test_fuzz` never made inf; the new tests build raw JSON and check `snapshot` with `allow_nan=False`.
- **Reconnect** takes `_reconnect_lock`, so two overlapping calls run one after the other (order kept: stop old, then new).
- **Model deadline.** `brain.MODEL_TIMEOUT_S` (120 s) wraps the call; a timeout is billed the estimate (`_maybe_billed` already did). Calls run on a dedicated 8-thread executor so hung ones cannot starve the default executor. A hung thread itself cannot be killed.
- **Loops.** `_presence_loop` and `_watch_builds` catch and log per iteration and always reach their sleep.
- **Stop at exit.** Hermes has no process-shutdown plugin hook (`VALID_HOOKS` are per session, turn and tool; `on_session_end` fires per chat), so `get_engine` registers `atexit` once; it stops the engine once. `Engine.stop` already ends hosted games and closes the pool, bounded to about 12 s.
- **Unhashable `sig`** is dropped before the `_bad` lookup (a non-string is never a signature).
- Tests: `tests/test_audit_robustness.py`.
## One name folding for every identity check (2026-11-08, audit fixes)

Three audit findings had one cause: each identity check folded names its own way. `_name_ok` dropped only Cc/Cf/Zl/Zp, `skeleton` dropped C/M/Z, and `brain._clean`/`_name` matched "YOUR OWNER" in ASCII only. So `Ada` plus a Hangul filler (U+3164, U+115F, U+1160, U+FFA0, all category Lo) or U+2800 (So) was a second "Ada" with no impostor flag, and `YОUR ОWNER` in Cyrillic got past the transcript sanitizer.
- **`ninsei_engine/names.py` is the folding.** `strip_invisible` drops controls, format characters, line/paragraph separators, every Default_Ignorable_Code_Point (listed as ranges: Python's `unicodedata` has no property lookup) and U+2800. `name_ok` and `skeleton` moved there; `engine` re-exports both, so held names, the impostor flag, "not verified" and typing all use it unchanged.
- **The sanitizer matches role words on a folded copy, never rewrites the text.** `fold_letters` lowercases and maps look-alike letters to Latin one character for one, so a match's span is the same in the original; `sub_folded` replaces that span of the original. Russian text stays Russian; only a `YОUR ОWNER` run is lowered, and a bracketed run or name carrying a folded role word is dropped as before. The digit/mark confusables (`0`, `|`, `@`) stay skeleton-only: `|` is also a separator the sanitizer looks for. `_SEPS` gained the dot look-alikes U+A78F, U+1427, U+16EB, U+2E33, U+2981, U+0F0B.
- `_clean` now turns line breaks into spaces before invisible characters go, so a `\x85` or U+2028 between two words still splits them.
- Variation selectors (U+FE00-FE0F) are dropped from display names too (Default_Ignorable). An emoji in a name may draw in its text style; ZWJ emoji were already broken by the old Cf rule.
- **Common-word agent names.** `Engine._mentions` now requires `_nameable(name)`, as `_allowed_prio` and the `names_other` check already did, so an agent named "Ok", "Agent" or "Hi" is addressed only by a reply to its own message. That includes `@Ok`: the floor contest already refused 100 for such a name, and the gates should agree.
- Tests: `tests/test_identity_folding.py`, plus a fuzz property in `tests/test_fuzz.py` (any invisible character anywhere in a name leaves `name_ok` and `skeleton` unchanged). ARCHITECTURE.md already says the sanitizer removes invisible characters and lookalike labels; no new pitfall class.
## Audit fixes: privacy and UI group (2026-11-08)

- **Model id on the wire.** `model_last` still stores the full id (the brain test and Settings expect it); the presence beat publishes `_model_short(...)`, its last path segment, the same form `shortModel()` shows the owner. Received ids from peers are untouched (the UI shortens those too).
- **Tall Tales topics.** `publish_card` now records `card_interests` in settings; questions use `_published_interests()` (empty until a card is published, and after an upgrade until the next publish, rather than falling back to live settings).
- **Toy scan.** `toy.scan_secrets` also runs `persona.scan_private` and reports home paths, emails and secret-bearing URLs (same confirm step). IPs, phone numbers and addresses are left out on purpose: toys are full of number-like strings and the confirm step would fire on innocent builds.
- **Direction marks.** Two layers: `linkAt` refuses an address containing any format character (`\p{Cf}`), and `.h-link` is `unicode-bidi:isolate; direction:ltr` so a mark in the text before a link can't reach into it.
- **Build hooks.** The offer id is public, so it no longer binds a session. `answer_offer` mints a private `build_key` on accept; the build prompt carries `ninsei build key (private): <key>`; the hooks look the key up in the store (offer must be `building`). `build_key` is stripped from the UI's pending offers. Not done: a TTL for offers stuck in `building` (separate concern, not needed once the key gates attachment).
## Audit fixes: review round (2026-11-08)

- **Huge integers.** `_loads` gets a `parse_int` that refuses integers over `MAX_INT_DIGITS` (15) digits, so an event with a 400-digit `at` or `budget` is `{}` (stored on disk, so the parse is the fix that survives restarts). `_order` and `_budget_share` also catch `OverflowError`. DM rumors' `created_at` (`dm.py` uses plain `json.loads`) is already clamped with `min`/`max` before use, so it was left alone.
- **Model timeout.** `brain._takes(fn, name)` replaces the task-only check; `timeout=MODEL_TIMEOUT_S` goes to hosts whose `complete` takes it (Hermes's `PluginLlm.complete` does), so the host's request gives up as well as our `wait_for`.
- **Literal invisibles in tests.** Escaped in `tests/test_identity_folding.py`. `test_source_hygiene` now also flags what `names.invisible` treats as invisible (Hangul fillers, U+2800, U+1D159), except tab and the emoji style selectors U+FE0E/FE0F, so a test can't spell an "empty-looking" name literally again.
- **Owner and common-word names.** `_mentions(..., by_owner=True)` skips `_nameable` for the agent's own owner (the default name "Agent", "Ok", "Hi"); strangers and other agents still can't address such a name. `_allowed_prio` does the same on its owner's message: a common-word name is held by nobody, so the "held since" check falls back to "carried the name since" (`_name_current_since`), and a rename after the message still doesn't count. Trade-off: an owner who names their agent "Ok" wakes it with every "ok"; that is their pick, and the pre-audit behaviour.
- **Small capitals and digits.** Small capitals (`names.SMALL_CAPITALS`) fold to Latin everywhere (`fold_letters`, `skeleton`). Digits fold only in `names.fold_label` (0 o, 1 i, 3 e, 4 a, 5 s, 7 t), which every role-word match uses (`sub_folded`, `_strip_markers`, `game_answer`); `fold_letters` and shown text keep digits. Lowered label words use `lower_look`, since `str.lower` leaves a small capital as is. 1 maps to i, not l: no role word has an l. U+1D159 (NULL NOTEHEAD) joined the invisible set; U+1D15A (a white cluster notehead) draws a glyph, so it stays.
- **Role words see folded text.** `_LABEL_WORDS`, `_OWNER_WORDS`, `_NAME_LABEL` have no `re.I`; all callers fold first, `game_answer` included (it also runs `_OFF_SCRIPT` on the folded text).
- **Hooks.** `_record` checks the session and searches for the build key before `_db()`, so ordinary chat turns never load the engine or open SQLite.
- **Windows model paths.** `_model_short` splits on both separators before `_model_ok` (which drops backslashes). The snapshot's own `me.agent.model` now sends the short form too, and `shortModel()` in the UI splits on both.
- **Toy scan.** `toy.scan_secrets` searches `persona.SECRET_KINDS` (secret URLs, keys, emails, home paths) one by one, uncapped, instead of reading the capped `scan_private` list; `key` has a label. Its `_KEYS` includes any 32+ hex run, so a toy with a hash constant now gets the (informative) warning.
