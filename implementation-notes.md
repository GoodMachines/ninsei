## UI (agent)
- **One source, two outputs, no npm.** `ui/*.js` is plain JS written against two tiny interfaces: `P` (platform: rest, timers, toasts, clipboard, storage, animation loop, `openBuild`) and `K` (kit: Button, Input, Dialog, Icon, Tip, Toggle, Toy). `scripts/build_ui.py` concatenates `ui/platform/<kind>_head.js` + `ui/*.js` + `<kind>_tail.js` into `desktop/plugin.js` (ESM) and `dashboard/dist/index.js` (IIFE), unminified, and refuses JSX or non-SDK imports. `--check` exits 1 when an output is stale.
- **Desktop imports the SDK as a namespace** (`import * as sdk`) so newer pieces (`registerSettingsPage`, `host.composer`, `createBudgetedLoop`, `ToggleRow`, `pet`) are feature-detected instead of failing module load on an older Desktop.
- **Theme:** every colour is a `--h-*` token mapped per platform onto `--ui-*` (Desktop) or `--color-*` (dashboard). Agent colour = the theme's own foreground rotated to the agent's hue (`oklch(from var(--h-fg) l 0.15 H)`) mixed 64% into the background, so faces read mid-tone on light and dark themes; plain accent is the fallback where relative colour syntax is missing.
- **Motion:** one damped-spring solver (semi-implicit Euler, 240 Hz substeps) on one shared loop that parks when nothing moves (`createBudgetedLoop` on Desktop, a self-parking rAF in the browser). Springs write to the DOM directly, never re-render React. Used for message/draft/toast entrance, the budget ring, the countdown ring, a face "pop" on state change, and scrolling a running toy into view. Face idle loops (blink, scan, talk, clock) are CSS keyframes. `prefers-reduced-motion` jumps springs to their target and stops keyframes.
- **Live updates:** Desktop listens to `plugin.hearth.changed` and polls `/state` (5 s with no Hearth view mounted, 2 s with one, 1 s while a game runs); the browser polls on the same schedule. A snapshot identical to the last one does not re-render.
- **Dashboard sizing:** the tab mounts inside the dashboard's scrolling `<main>`, so the page measures its own top edge and sizes to the rest of the window; only the timeline and the pinned stack (game, drafts) scroll.
- **Verified in the browser** (dashboard tab, Maya on :9311 and Sam on :9312): room, Lobby, card preview, settings, toy Run in a sandboxed iframe, narrow layouts. Vote/reveal/fakes phases, impostor chip, budget line, drafts tray, open offer and the review dialog were checked by patching `SDK.fetchJSON` in the page to inject those states (no extra model spend). **Not verified:** anything Desktop-only (route, nav row, status chip, palette, settings page, pet line, composer hand-off); it is built against the docs and `sdk/index.ts`.
- **API gaps noticed (not changed):** game `ends_at` has no phase start or duration, so the countdown ring takes its full length from the longest remaining time it has seen; reveal `authors`/`picks` are pubkeys only, so names come from the room's member list (a player who left shows as "someone"); both test agents still carry the engine default face (`hue 28, round`), so Ada and Bo look alike until someone picks a face.

## Widgets + theme (agent)

- **Chat cards.** Two transcript directives, registered on `sdk.TRANSCRIPT_DIRECTIVE_AREA` (skipped on a Desktop without it): `::hearth-offer{id="<64-hex offer id>"}` and `::hearth-tales{room="<room id>"}`. Attribute values need double (or single) quotes, or Desktop's parser ignores them. Code is `ui/65_cards.js`, registered in `desktop_tail.js`; the dashboard bundle carries the code but never registers it.
- **Untrusted attributes.** Shape check (64-hex / 8-64-hex), then a lookup in the backend's own `/state`; a miss renders a small "Hearth: not found" chip, a missing backend renders "Hearth: not available". All text is rendered as text.
- **Offer card.** Title, pitch, state, owner. Yours + open: Accept (calls `/offers/answer`, then the same `P.openBuild` hand-off as the Hearth page: new chat, task in the composer, nothing sent) and Not now. Ready: Share to room, with an inline "Share the built file with #room?" confirm because there is no preview here. Other people's offers are read-only.
- **Tales card.** Reuses `TallTales` (fake/vote/reveal/scoreboard) with a card-local store whose `post` hits `/game/fake` and `/game/vote`; polls `/state?room=` every second. `autoFocus` is off in cards (`quiet`), so a card appearing never steals the composer.
- **Hidden turns: not wired up the way the brief assumed.** `window.hermes.send()` exists only inside the sandboxed preview frame (`inline-preview-directive.tsx` injects it). A plugin React component runs in the app window, where nothing defines it, and the SDK's `host.composer.submit()` sends a visible turn (no `displayKind: 'hidden'` option). So `tellAgent()` feature-detects `window.hermes.send` and does nothing when it is absent, rather than posting visible chatter. Decline and share call it (<=500 chars, one per second); Accept does not, because it moves to a new chat. Backend routes do all the real work.
- **Read side effect.** `/state?room=` marks that room read. The offer card therefore only fetches a room when it has nothing cached or the offer changed state; the tales card fetches its room every second while mounted (viewing it counts as reading).
- **Getting directives into chats.** `build_prompt` now tells the agent to open its reply with the offer directive (test added). `hearth_status` returns `chat_cards`: offer directives for open/building/ready offers, a tales directive per room, and a one-line how-to. The model only has the store (no live game state), so the how-to says to use a tales line only when it is telling the user about a running game.
- **Theme "Hearth"** (`name: 'hearth'`, `sdk.THEMES_AREA`; light and dark palettes). Warm paper (#f6efe4) and banked embers (#1f1a17), accent derived from Hearth's default agent hue (28). Listed in the picker only; nothing calls `setTheme`/`requestTheme`. Contrast checked with the WCAG formula the SDK's `contrastRatio` uses: every text pair >= 5.0:1 (lowest: primary on card, light), most 6-12:1.
- **Not verified in the app:** the directive rendering, button flows, the `window.hermes` availability, and the picker entry. All checked statically against `transcript-directive.tsx`, `lib/transcript-directives.ts`, `themes/types.ts` and `user-themes.ts`.
## Plan cap (agent)

Optional second cap, off by default: `plan_pct` (0 = off, 1-100) means "Hearth may use at most N% of my Nous plan per day". Code is `hearth_engine/plan.py`; tests are `tests/test_plan_cap.py`.

- **How billing is read.** The Desktop "billing" catalog plugin reads `billing.state` from the renderer with `host.request('billing.state')` (`desktop/plugin.js` in anotherchu/billing at 2dfcc8e, line ~45). That is a JSON-RPC method in `tui_gateway/methods_session.py:1829`, so a Python plugin can't call it. The RPC is a thin wrapper over `agent.billing_view.build_billing_state()` and the `usage` block of `agent.billing_usage.build_usage_model()`. Hearth calls the latter in-process (sync, network, 8 s timeout, run with `asyncio.to_thread`). Hermes does the auth itself, so Hearth never touches `auth.json`, tokens or `.env` (catalog rule 11). `billing.state` carries `balanceUsd` (total, top-ups included); the usage model has the plan allowance on its own (`plan_bar.remaining_usd`), which is what the cap needs. The public `agent.account_usage.fetch_account_usage("nous")` returns nothing because Nous has no fetcher there.
- **Known warning.** `hermes plugins validate .` passes but prints the rule-9 "private core imports" warning for `agent.billing_usage` and `agent.usage_pricing`. No public seam exists for either (checked against `plugin_validate_private_imports._PUBLIC`). Both imports sit in one function each, fail open, and can break on a Hermes release; the cap then goes inert and the token budget carries on.
- **`pre_llm_call` does not gate `ctx.llm.complete`.** It is fired from `agent/turn_context.py:811` (`_collect_pre_llm_call_context`) once per agent user turn. `agent/plugin_llm.py` never calls hooks. So no hook is registered and `plugin.yaml` is unchanged; the cap is enforced in Hearth's own call path: `Brain._complete` awaits `PlanCap.preflight()` before `reserve`, and raises the same `BudgetExhausted`. The rest notice and `system: waiting` state follow the existing path. Owner's normal Hermes chats are untouched.
- **Dollars.** Billing reports no per-call cost: `PluginLlmUsage.cost_usd` exists but `_extract_usage` never sets it (agent/plugin_llm.py:337-358). So cost is `usage.cost_usd` if a future host sets it, else Hermes's price table (`estimate_usage_cost`), else a flat $10 per million tokens (`cost_basis` in `/state` says which: reported, estimated, fallback, not-nous). Only results whose provider is Nous count; Hearth calls routed to another provider (Justin's default is openai-codex) add $0.
- **Snapshot.** The first call (or the background probe at engine start / when the setting is saved) after local midnight stores `plan_snapshot` in kv; the cap is snapshot x N%. If Hearth first runs at 3 pm, the snapshot already excludes the morning's spend by everything else. A failed read is retried after 60 s, not per call.
- **Overshoot.** The gate checks dollars already settled, so calls in flight when the cap is crossed can finish; the token budget's atomic reserve doesn't have this. At most a few small calls.
- **`/state` budget** gains `plan_pct, available, checked, plan_cap_usd, plan_used_usd, plan_snapshot_usd, cost_basis`. `pct` (the ring) is the larger of token use and cap use. Settings gains one field and one line under the ring ("Not on a Nous plan" when unreadable).
- **Not verified live.** No Nous plan available here (default model is openai-codex), so the real `build_usage_model` read, the real price lookup and the real `res.provider` string on a Nous call are verified by reading source only. Tests use a stubbed source and cost.

## Platform (agent)

- **Shape as briefed, no changes forced.** One global chat (`chat_id: private`, name "Hearth · private line"), not one per room: per-room chats would suggest the room is context, and it never is. Owner messages go UI → `private_line` table → adapter → gateway; replies go `send()` → same table. Post to room goes through `store.queue_draft` (origin "your Hermes").
- **Authorization: `trusted_inbound=True`.** Without it the gateway treats `owner` like a stranger and answers with a pairing code. The docs say "never set it for a chat platform"; I set it because this platform has no remote sender: inbound rows come only from the local, auth-gated UI writing an owner-only file. Validate shows it as a disclosure line. If a reviewer objects, the fallback is `allowed_users_env="HEARTH_ALLOWED_USERS"` with the user setting `owner`, which is friction. On an older core that rejects the field, registration retries without it (pairing then applies).
- **Enablement.** No `is_connected`, so the gateway enables `hearth` whenever `check_fn` is true; `check_fn` is passive (the store file exists, never creates the folder). `env_enablement_fn` seeds the home channel, which silences the "no home channel" prompt and makes `deliver=hearth` cron work; `standalone_sender_fn` covers cron outside the gateway.
- **Polling, 1 s.** Hermes has no cross-process wake-up a plugin can use, so the adapter polls an indexed query. Heartbeat every 10 s; the UI calls the gateway "down" after 45 s and says messages wait.
- **`display_tier: low`.** No streaming or tool-progress chatter in the thread; a typing indicator instead (`send_typing` writes a kv stamp). `edit_message` is implemented anyway.
- **Isolation.** `plugins.isolation: host` refuses `register_platform` (adapters must run in the gateway). The call is caught and logged; the validator's isolation line now says "in-process only". I kept the call literal (`ctx.register_platform`) so the static audit sees it.
- **Verified:** 64 tests (51 old + 13 new; the adapter runs against a stand-in for the gateway classes), `hermes plugins validate .` passes, and a smoke against Hermes's real `BasePlatformAdapter`/`PlatformEntry`/`MessageEvent`. Also a real `hermes gateway run` in a throwaway `HERMES_HOME` in my scratchpad (standalone, TELEGRAM_* stripped, no model creds, 30-45 s timeouts): the gateway auto-enabled `hearth`, took the queued owner message without pairing, started an agent turn (failed on the dummy model, as intended), and `/help` came back into the private thread. UI checked in an isolated scratch dashboard (port 9391): thread, private badge, gateway-down notice, send, Post to room (draft landed, zero events), narrow layout. Scratch homes deleted.
- **Not verified:** a real model reply on `hearthmaya` (its gateway, PID 61600, was started by someone else during my run and Desktop owns its engine, so I left it alone); the Desktop render (built, not opened); Desktop codicons `lock` and `reply` (assumed present).
